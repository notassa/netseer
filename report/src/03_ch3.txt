@chapter CHAPTER 3: METHODOLOGY
@h2 3.1 Introduction
This chapter describes the methodology used to design, develop and evaluate NetSeer, the proposed alert interpretation system. The project follows a Software Development Life Cycle (SDLC) approach, and the Rapid Application Development (RAD) model is selected as the development methodology. This chapter discusses the RAD model and the reasons for its selection, the activities carried out in each development phase, the system requirements derived for NetSeer, the evaluation plan, the hardware and software requirements, and the project planning.
@h2 3.2 Rapid Application Development (RAD) Model
The RAD model is an incremental software development model that emphasises rapid prototyping, active user involvement and short development cycles, typically lasting between 60 and 90 days (Pressman & Maxim, 2020). As shown in Figure 3.1, the model consists of four phases: requirements planning, user design, construction and cutover. Rather than completing the entire system in a single pass, RAD allows the main modules to be built early, tested repeatedly and refined based on continuous feedback.
@figure assets/fig3_1_rad.png | Figure 3.1: Rapid Application Development (RAD) Model | 6.0
@source (Source: https://medium.com/@myelmarc/sdlc-methodology-101-a-beginners-guide-to-rapid-application-development-rad-492ab88de7ef)
RAD is particularly effective for projects with well-defined user interfaces, modular components and a need for fast delivery (Pressman & Maxim, 2020). For NetSeer, usability and user acceptance are as important as technical correctness, because the target users are non-expert administrators. The iterative nature of RAD allows the dashboard and the interpretation output to be improved through repeated prototyping and feedback from Oriental Tech, and it allows weaknesses to be identified and corrected early in development. The modular ACP pipeline also maps naturally onto RAD iterations, since each stage can be built, tested and demonstrated independently.
@h2 3.3 Phases of Rapid Application Development (RAD)
@h3 3.3.1 Requirements Planning
The first step in the requirements planning phase was to define the main problems facing small-network administrators. These administrators include home-office users, small-business owners and educational-laboratory managers who want to monitor network security but lack technical security experience. The primary user is a small-network administrator with basic networking skills but no formal training in cybersecurity, represented in this project by the administrators of Oriental Tech. Requirements were derived from the literature review, an analysis of existing IDS tools, discussions with Oriental Tech, and observation of how non-expert users interact with security dashboards.
This phase focused on the specific security monitoring needs of small networks, including the detection of threats such as port scanning, brute-force attempts and malware communication without overwhelming the user with false-positive alerts. Once the requirements were gathered, they were classified into functional requirements, non-functional (quality) requirements and constraints, and each requirement was prioritised using the MoSCoW method (Must, Should, Could, Won't) so that the essential capabilities are delivered first in the time-boxed RAD iterations. The main constraints of the project are the absence of a GPU on the target hardware, which limits the size of the local language model; the passive nature of enrichment, which depends on what is present in the captured traffic; and the dependence on Suricata rule coverage, since NetSeer can only interpret alerts that Suricata generates.
@h3 3.3.2 User Design
The user design phase translated the gathered requirements into the structure, interface and processing flow of NetSeer. Because the target users are non-expert administrators, user-focused design was prioritised, and every design decision was evaluated against whether it would help a non-technical user understand what is happening on their network. The core usability problem addressed in this phase is that raw Suricata alerts are too technical for non-expert users to understand. In line with RAD, low-fidelity wireframes and a clickable prototype were reviewed with Oriental Tech before construction began.
Several diagrams were developed to describe system operation and user interaction. The system architecture diagram (Figure 3.2) shows the overall structure of NetSeer, comprising the web dashboard, the backend with its data acquisition, context enrichment, Alert-Context Processing and interpretation components, and the database. The activity diagram (Figure 3.3) depicts the processing flow from PCAP upload and Suricata processing, through Alert-Context Processing (ACP), to the AI-assisted explanation displayed on the dashboard. The block diagram (Figure 3.4) summarises the data flow from the network data source to the user. The use case diagram (Figure 3.5) describes the main functions available to the User and Administrator roles, and the misuse case diagram (Figure 3.6) describes the threats that could be directed at NetSeer itself and the mitigations that address them. @h3 3.3.3 Construction
The system modules are built and integrated during the construction phase according to the approved design, in short iterations that each end with a working, demonstrable increment, testing and a feedback session. The construction phase is organised into the following iterations, which follow the order in the project Gantt chart (Figure 3.8):
@bullets
- Iteration 1 (web system and context enrichment): the FastAPI web application, first-launch administrator setup, authentication and role-based access control, network selection for offline mode, multi-file PCAP upload and Suricata processing, the eve.json parser, alert normalisation, device discovery and attribution, the analyses browser, and the Network, Alerts and Devices pages.
- Iteration 2 (context processing): aggregation, correlation, incident-level enrichment, risk prioritisation, device risk and network health, the NetSeer configuration settings, and the Incidents and Home pages, together with the UNSW-NB15 validation scripts used to calibrate the time windows and risk factors.
- Iteration 3 (interpretation): the knowledge base and retrieval module (RAG), evidence-package construction, the Prompt Maker, the language-model integration through Ollama, the output verifier and the AI page.
- Iteration 4 (real-time monitoring): interface selection and detection, live capture through the mirror port, incremental processing of new alerts, device attribution for newly seen devices and storage of each session as a separate analysis, reusing the same pipeline.
@endbullets
The web dashboard is built with FastAPI, Jinja2 templates and Chart.js, and the prototype is tested and debugged continuously with automated unit tests and a fixed set of sample PCAP files that serve as a regression check after each iteration.
@h3 3.3.4 Cutover
The cutover phase covers final integration, testing and preparation of the system for evaluation. Remaining defects are fixed, and the system is deployed on the target hardware for local operation as a set of system services behind an Nginx reverse proxy with TLS, accessible only from the local network. A security hardening review is carried out against the OWASP ASVS 5.0 checklist, and the evaluation described in Section 3.4 is performed. This phase ensures that the system functions correctly and achieves the project goals before the final presentation.
@h2 3.4 Evaluation Plan
The proposed system is evaluated in four parts, corresponding to its main components.
First, Suricata alert validation assesses the alerts generated from the UNSW-NB15 dataset against the dataset ground truth, using timestamp, source and destination addresses, ports, protocol and attack category where available. Each alert is classified as a true positive, a false positive or uncertain. This validation characterises the detection input to the proposed system; it does not claim that the proposed system improves Suricata detection.
Second, the ACP evaluation examines the reduction in alert volume, the correctness of aggregation, the usefulness of correlation and the traceability of risk prioritisation.
Third, the AI interpretation evaluation measures the faithfulness, factual accuracy and coverage of the generated explanations, the unsupported-claim rate, the clarity of stated uncertainty, the understandability and usefulness of the explanations, and the relevance of the recommended actions.
Fourth, the system evaluation measures processing time, dashboard usability, local deployment feasibility and resource usage on the target hardware, together with a user comprehension study that compares users' understanding of raw Suricata alerts with their understanding of NetSeer explanations. Where host identity, operating system or passive fingerprinting data is unavailable in the dataset, this is treated as a dataset limitation and the corresponding context is marked as unknown rather than fabricated. Table 3.3 summarises the metrics.
@table Table 3.3: Evaluation Metrics | 20,28,52
Part | Metric | Definition or Method
Suricata validation | True positive, false positive and uncertain rates per attack category | Alerts matched to UNSW-NB15 ground-truth records by 5-tuple and time window.
ACP | Alert volume reduction | 1 minus the number of incidents (and alert groups) divided by the number of raw alerts.
ACP | Aggregation and correlation correctness | Proportion of groups and incidents whose alerts share one ground-truth attack label, with manual review of a sample.
ACP | Traceability | Proportion of incidents that link to their raw alerts and store a complete risk factor breakdown.
AI interpretation | Faithfulness | Supported claims divided by total claims, following Es et al. (2024).
AI interpretation | Unsupported-claim rate | Claims flagged by the verifier or by manual review divided by total claims.
AI interpretation | Accuracy, coverage, uncertainty and usefulness | Manual review of sampled incidents and Likert-scale ratings by users and an expert from Oriental Tech.
System | Processing time and resource usage | Seconds per megabyte of PCAP, LLM latency, CPU and memory usage on the target hardware.
System | Usability | System Usability Scale (SUS) questionnaire (Lewis, 2018).
System | User comprehension | Quiz score and confidence when interpreting raw Suricata alerts compared with NetSeer explanations.
@endtable

@h3 3.5.3 Costing
All hardware and software components used in the proposed system are free and open-source, with the exception of an optional cloud large-language-model API and optional threat-intelligence services, whose cost depends on the user's own subscription. The system is designed to run entirely on a locally hosted, quantised model, avoiding recurring subscription costs.
